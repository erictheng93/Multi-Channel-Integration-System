0.2 稽核後新發現：在線名單被污染

未指派團隊的對話走全域廣播，MessageBroadcaster 依自己的在線名單 userConnections 發送。但 deliverToUser() 會把每一個送過的使用者 stub 寫進同一個 Map，而團隊廣播會送給 D1 查出的全部成員，所以離線者被寫進名單、被持久化、而且永遠不會被移除。結果每則訊息打 11 個 UserConnection，實測同時在線只有 3–5 人。UserConnection 沒有離線佇列，送給離線者的事件本來就被丟掉。

#103 的修法：deliverToUser 不再寫入名單；/batch-events 回傳即時 socket 數，回報 0 的使用者在全域廣播後被移出名單並持久化一次。休眠喚醒時 socket 數在建構子內同步由 getWebSockets() 重建，所以在線者不會被誤刪。

已經乾淨、不需要動的部分

7. 部署安全規則

DO 類別刪除是單向的，而且會鎖死 rollback。Cloudflare 文件確認三件事：deleted_classes 會永久刪除 namespace 與全部資料，沒有回收桶；任何 DO lifecycle 變更之後，wrangler rollback 一律拒絕回到變更前的版本；lifecycle 變更應該單獨部署，不與其他程式碼混在一起。本專案的 bun run deploy 直接執行 wrangler deploy，沒有針對遷移的 dry-run 關卡。

  1. Tier 1–3 全部不含 DO lifecycle 變更，每一支都能用 wrangler rollback 回退。
  2. v7 遷移從 chore/remove-api-metrics 拆出。該分支保留「移除 middleware、呼叫端、binding」，並留一個約 10 行的 MetricsCollectorDO 空殼 class（v6 已建立此 class，不 export 又沒有 delete 遷移會被拒絕部署）。閒置 namespace 的計算成本為零，儲存只有一筆小 value。要刪就等整體優化穩定後，單獨一次 deploy 只含 v7。將來若要刪 LatestMessageCacheCoordinator，同樣規則。
  3. 部署前 git status 必須乾淨。wrangler deploy 打包的是工作樹，另一個 session 的未提交 DO 編輯曾經被一起送上去。
  4. 每支 PR 描述寫清楚「這條 alarm 鏈怎麼停」，這是 CLAUDE.md 已有的規則，對 1a 尤其重要。
  5. 1c 動手前先 wrangler tail 幾分鐘，確認沒有外部探針打 /api/monitoring/health。
  6. 一個 commit 一件事：上面是 5 支獨立的 PR。

附錄 B：稽核方法

  • 四個獨立的程式碼稽核平行進行：WebSocket 三件組（ConversationRoom、UserConnection、MessageBroadcaster）；Customer 兩件組（CustomerConversationDO、CustomerMessageDO）；快取、延遲投遞、鎖與限流（LatestMessageCacheCoordinator、DelayedMessageScheduler、LockCoordinator、RateLimiterDO）；Worker 端每個業務事件的 DO 請求追蹤，含 cron、前端輪詢與 socket 心跳。
  • 七個浪費點中影響最大的五項（W1、W2、W3、W5、W6）由第二人直接讀原始碼再確認，包含 grep 全域確認 W2 無讀者、W5 無 importer。
  • 定價與遷移規則取自 Cloudflare 官方文件：durable-objects/platform/pricing、durable-object-lifecycle、durable-objects-migrations、versions-and-deployments/rollbacks、gradual-deployments/with-durable-objects。
  • 所有「每日規模」數字都是以 30 位 agent、200 個活躍對話、每日 3,000 則訊息、N = 10–30 推算，不是帳單實測。唯一需要實測證實的是 W1。
