## 1. 簡介

### 1.1 目的
本功能需求規格書(FRS)文件定義了多通路客服支援系統的詳細功能需求。它為開發人員、測試人員和利害關係人提供全面指南，以理解系統預期的行為和功能。

### 1.2 範圍
FRS涵蓋系統的所有功能面向，包括：
- 使用者認證和授權
- 多通路訊息處理
- 對話管理
- 團隊和角色管理
- 檔案附件處理
- 延遲訊息系統
- 分析和報告
- 系統管理

### 1.3 文件結構
- **第2節**：系統概述和架構
- **第3節**：使用者管理功能
- **第4節**：對話管理功能
- **第5節**：訊息處理功能
- **第6節**：團隊和角色管理功能
- **第7節**：檔案管理功能
- **第8節**：延遲訊息功能
- **第9節**：分析和報告功能
- **第10節**：整合功能

## 2. 系統概述

### 2.1 功能架構
系統實施模組化、基於處理器的架構，包含以下功能組件：

#### 2.1.1 核心處理器
- **認證處理器** (`auth-main.ts`)：使用者登入、註冊和會話管理
- **對話處理器** (`conversation-main.ts`)：對話生命週期和指派管理
- **訊息處理器** (`delayed-message-main.ts`)：訊息處理和延遲訊息
- **團隊處理器** (`team-main.ts`)：團隊和成員管理
- **系統處理器** (`system-main.ts`)：系統設定和健康監控
- **客戶處理器** (`customer-main.ts`)：客戶資料管理

#### 2.1.2 整合層
- **平台適配器** (`platform-adapter.ts`)：多通路平台抽象
- **Webhook處理器** (`webhook.ts`)：外部平台webhook處理
- **活動服務** (`activity-service.ts`)：系統活動追蹤和記錄

### 2.2 資料流架構
```
外部平台 (LINE, Facebook) 
    ↓ [Webhooks]
Webhook處理器 
    ↓ [處理]
平台適配器 
    ↓ [統一格式]
核心處理器 
    ↓ [業務邏輯]
資料庫層 (Drizzle ORM)
    ↓ [儲存]
Cloudflare D1/KV/R2
```

## 3. 使用者管理功能

### 3.1 使用者認證

#### 3.1.1 使用者登入 (FR-AUTH-001)
**描述**：透過電子郵件或使用者名稱憑證認證使用者
**處理器**：`auth-main.ts:22-100`

**輸入**：
- 電子郵件地址(選用)
- 使用者名稱(選用)
- 密碼(必填)

**處理流程**：
1. 驗證輸入參數(電子郵件/使用者名稱和密碼必填)
2. 清理輸入資料(去除空格)
3. 檢查使用者在資料庫中是否存在
4. 驗證帳戶狀態(啟用/停用)
5. 使用bcrypt比較驗證密碼
6. 檢查密碼政策要求
7. 產生包含使用者資訊的JWT令牌
8. 在Cloudflare KV中建立會話記錄
9. 記錄認證活動

**輸出**：
- 成功：JWT令牌、使用者檔案、會話資訊
- 失敗：錯誤訊息與適當HTTP狀態碼

**業務規則**：
- 支援電子郵件和使用者名稱登入
- 非啟用帳戶無法認證
- 登入失敗嘗試有速率限制(每分鐘10次)
- "must_change"帳戶的密碼政策強制執行
- 所有認證嘗試的活動記錄

#### 3.1.2 使用者註冊 (FR-AUTH-002)
**描述**：透過邀請系統建立新使用者帳戶
**處理器**：`auth-main.ts:register`

**輸入**：
- 邀請令牌
- 使用者詳細資訊(姓名、電子郵件、密碼)
- 團隊指派(團隊/客服角色)

**處理流程**：
1. 驗證邀請令牌存在性和有效期
2. 驗證令牌未曾使用
3. 驗證使用者輸入資料
4. 使用bcrypt雜湊密碼
5. 在資料庫中建立使用者記錄
6. 根據邀請指派角色和團隊
7. 標記邀請為已使用
8. 產生初始JWT令牌
9. 記錄註冊活動

**輸出**：
- 成功：建立使用者帳戶，發出JWT令牌
- 失敗：驗證錯誤或邀請過期

**業務規則**：
- 僅透過有效邀請令牌註冊
- 一次性令牌使用
- 基於邀請類型的角色指派
- 團隊/客服角色的團隊指派為必填
- 使用bcrypt自動密碼雜湊

#### 3.1.3 密碼管理 (FR-AUTH-003)
**描述**：處理密碼變更和政策強制執行
**處理器**：`auth-main.ts:changePassword`

**輸入**：
- 目前密碼
- 新密碼
- 使用者認證令牌

**處理流程**：
1. 驗證目前密碼
2. 驗證新密碼要求
3. 檢查密碼政策設定
4. 在資料庫中更新密碼雜湊
5. 選擇性使現有會話無效
6. 記錄密碼變更活動

**輸出**：
- 成功：密碼更新確認
- 失敗：驗證錯誤或政策違規

**業務規則**：
- 需要目前密碼驗證
- 強制執行密碼強度要求
- 基於政策的密碼變更控制
- 安全性的會話無效化

### 3.2 使用者授權

#### 3.2.1 角色權限控制 (FR-AUTH-004)
**描述**：實施具有權限繼承的3層角色階層
**處理器**：`permission-service.ts`

**角色階層**：
- **管理員(第3級)**：系統全域存取，所有權限
- **團隊(第2級)**：團隊範圍管理權限
- **客服(第1級)**：對話特定權限

**處理流程**：
1. 從JWT令牌提取使用者角色
2. 確定操作所需權限等級
3. 檢查角色階層授權
4. 驗證團隊特定權限(團隊/客服角色)
5. 記錄授權決策

**業務規則**：
- 高級角色繼承低級角色權限
- 團隊/客服角色限制於指派團隊範圍
- 管理員角色繞過團隊限制
- 所有受保護操作需要權限檢查

#### 3.2.2 會話管理 (FR-AUTH-005)
**描述**：管理具有自動過期和續訂的使用者會話
**處理器**：`session-main.ts`

**處理流程**：
1. 登入時在Cloudflare KV中建立會話記錄
2. 請求時驗證會話存在性和有效期
3. 活動時刷新會話有效期
4. 自動清理過期會話
5. 支援會話終止(登出)

**業務規則**：
- 會話逾時：8小時不活動
- 使用者活動時自動會話刷新
- Cloudflare KV中的安全會話儲存
- 登出或安全事件時會話無效化

## 4. 對話管理功能

### 4.1 對話生命週期

#### 4.1.1 對話建立 (FR-CONV-001)
**描述**：從平台訊息建立新對話
**處理器**：`conversation-main.ts:create`

**輸入**：
- 平台識別符(LINE、Facebook)
- 使用者/客戶ID
- 初始訊息內容
- 平台特定後設資料

**處理流程**：
1. 驗證平台和使用者資訊
2. 檢查與客戶的現有對話
3. 建立具有唯一ID的對話記錄
4. 設定初始狀態為"待處理"
5. 根據平台規則關聯適當團隊
6. 建立初始訊息記錄
7. 觸發指派工作流程
8. 記錄對話建立活動

**輸出**：
- 對話ID
- 初始訊息確認
- 指派狀態

**業務規則**：
- 每個客戶每個平台一個活躍對話
- 基於平台的自動團隊指派
- 對話繼承平台訊息格式要求
- 初始狀態始終為"待處理"

#### 4.1.2 對話指派 (FR-CONV-002)
**描述**：將對話指派給客服或團隊
**處理器**：`conversation-main.ts:11-50`

**輸入**：
- 對話ID
- 目標團隊ID(選用)
- 目標客服ID(選用)
- 指派原因
- 請求使用者認證

**處理流程**：
1. 驗證指派操作的使用者權限
2. 檢查對話存在性和目前狀態
3. 驗證目標團隊/客服可用性
4. 更新對話指派欄位
5. 建立轉移歷史記錄
6. 通知指派的客服/團隊
7. 如適用，更新對話狀態
8. 記錄指派活動

**輸出**：
- 指派確認
- 更新的對話後設資料
- 轉移歷史記錄

**業務規則**：
- 指派需要"conversation:assign"權限
- 團隊主管可以在其團隊內指派
- 管理員可以跨所有團隊指派
- 維護指派歷史以供審計軌跡
- 向指派方發送通知

#### 4.1.3 對話狀態管理 (FR-CONV-003)
**描述**：管理對話狀態轉換
**處理器**：`conversation-main.ts:statusUpdate`

**狀態流程**：
```
待處理 → 進行中 → 已關閉
    ↓         ↓           ↓
[自動]   [手動]   [手動/自動]
```

**輸入**：
- 對話ID
- 目標狀態
- 狀態變更原因
- 使用者認證

**處理流程**：
1. 驗證狀態轉換規則
2. 檢查狀態變更的使用者權限
3. 更新對話狀態和時間戳記
4. 建立狀態歷史記錄
5. 觸發相關工作流程(通知、指派)
6. 更新分析指標
7. 記錄狀態變更活動

**輸出**：
- 狀態變更確認
- 更新的對話後設資料
- 工作流程觸發結果

**業務規則**：
- 狀態轉換必須遵循定義工作流程
- 客服只能修改指派對話狀態
- 團隊主管可以修改所有團隊對話狀態
- 維護狀態歷史以供報告
- 系統事件的自動狀態變更

### 4.2 對話操作

#### 4.2.1 對話轉移 (FR-CONV-004)
**描述**：在客服或團隊間轉移對話
**處理器**：`conversation-main.ts:transfer`

**輸入**：
- 來源對話ID
- 目標團隊/客服ID
- 轉移原因
- 使用者認證

**處理流程**：
1. 驗證轉移權限
2. 檢查目標可用性和容量
3. 建立包含後設資料的轉移記錄
4. 更新對話指派
5. 通知相關方
6. 為新客服更新客戶情境
7. 記錄轉移活動

**輸出**：
- 轉移確認
- 更新的指派資訊
- 通知傳送狀態

**業務規則**：
- 轉移需要適當角色權限
- 跨團隊轉移需要管理員或團隊主管核准
- 保留轉移歷史以供審計
- 通知客戶客服變更
- 轉移期間保持情境

#### 4.2.2 對話搜尋和過濾 (FR-CONV-005)
**描述**：基於多個條件搜尋和過濾對話
**處理器**：`conversation-main.ts:search`

**搜尋條件**：
- 客戶資訊(姓名、平台ID)
- 對話狀態
- 指派的客服/團隊
- 日期範圍
- 平台類型
- 訊息內容

**處理流程**：
1. 驗證搜尋參數
2. 應用基於角色的存取過濾器
3. 建立動態資料庫查詢
4. 使用分頁執行搜尋
5. 格式化結果與相關後設資料
6. 記錄搜尋活動以供分析

**輸出**：
- 分頁對話列表
- 搜尋結果後設資料(計數、應用的過濾器)
- 效能指標

**業務規則**：
- 搜尋結果依使用者權限過濾
- 客服只看指派對話
- 團隊主管看團隊對話
- 管理員看所有對話
- 使用索引優化搜尋效能

## 5. 訊息處理功能

### 5.1 訊息處理

#### 5.1.1 入站訊息處理 (FR-MSG-001)
**描述**：處理來自外部平台的訊息
**處理器**：`webhook.ts`

**輸入**：
- 平台webhook有效載荷
- 平台簽章/認證
- 訊息類型和內容
- 發送者資訊

**處理流程**：
1. 驗證webhook簽章和真實性
2. 解析平台特定訊息格式
3. 提取發送者和內容資訊
4. 找到或建立對話記錄
5. 建立包含後設資料的訊息記錄
6. 處理訊息內容(文字、媒體、檔案)
7. 如需要觸發對話指派
8. 向客服發送即時更新
9. 記錄訊息處理活動

**輸出**：
- 向平台的訊息確認
- 內部訊息記錄
- 客服通知
- 對話更新

**業務規則**：
- 所有入站訊息必須經過認證
- 使用時間戳記保持訊息順序
- 安全處理和儲存媒體內容
- 新客戶的對話自動建立
- 即時客服通知

#### 5.1.2 出站訊息處理 (FR-MSG-002)
**描述**：透過平台API向客戶發送訊息
**處理器**：`message.ts:send`

**輸入**：
- 對話ID
- 訊息內容和類型
- 發送客服ID
- 平台特定格式選項

**處理流程**：
1. 驗證對話的客服權限
2. 為平台格式準備訊息內容
3. 透過平台API發送訊息
4. 在資料庫中儲存訊息記錄
5. 處理平台回應和確認
6. 更新對話時間戳記
7. 處理訊息傳送狀態
8. 記錄出站訊息活動

**輸出**：
- 平台傳送確認
- 內部訊息記錄
- 傳送狀態更新

**業務規則**：
- 客服必須有對話存取權
- 驗證平台要求的訊息格式
- 追蹤傳送確認
- 失敗訊息排隊重試
- 按平台規則應用速率限制

#### 5.1.3 訊息內容處理 (FR-MSG-003)
**描述**：處理不同訊息類型和內容格式
**處理器**：`message.ts:processContent`

**支援的訊息類型**：
- 文字訊息
- 圖片附件
- 檔案附件
- 位置資料
- 快速回覆
- 豐富內容(卡片、輪播)

**處理流程**：
1. 從內容識別訊息類型
2. 驗證內容格式和大小限制
3. 處理媒體內容(上傳至R2儲存)
4. 產生檔案存取的安全URL
5. 建立包含適當後設資料的訊息記錄
6. 處理平台特定格式
7. 記錄內容處理詳細資訊

**輸出**：
- 處理過的訊息內容
- 檔案儲存URL
- 格式化的訊息記錄

**業務規則**：
- 按平台強制執行檔案大小限制
- 媒體內容儲存在安全雲端儲存
- 使用適當存取控制產生內容URL
- 應用平台特定格式
- 檔案上傳的病毒掃描

### 5.2 延遲訊息

#### 5.2.1 訊息排程 (FR-MSG-004)
**描述**：排程延遲傳送的訊息
**處理器**：`delayed-message-main.ts:schedule`

**輸入**：
- 對話ID
- 訊息內容和類型
- 延遲持續時間(1-120秒)
- 發送客服ID

**處理流程**：
1. 驗證延遲參數和權限
2. 建立延遲訊息記錄
3. 在Cloudflare Queue中排程訊息
4. 為UI產生倒數計時器
5. 儲存排程後設資料
6. 提供取消功能
7. 記錄排程活動

**輸出**：
- 排程確認
- 延遲訊息ID
- 倒數計時器資訊
- 取消令牌

**業務規則**：
- 延遲範圍：1-120秒
- 訊息可在發送前取消
- 客服必須有對話存取權
- 防止排程衝突
- 可靠性的佇列重試邏輯

#### 5.2.2 訊息撤回 (FR-MSG-005)
**描述**：在傳送前取消排程訊息
**處理器**：`message-recall-service.ts`

**輸入**：
- 延遲訊息ID
- 撤回原因
- 使用者認證

**處理流程**：
1. 驗證訊息存在且為待處理
2. 檢查撤回的使用者權限
3. 從傳送佇列移除訊息
4. 更新訊息狀態為"已取消"
5. 記錄撤回活動
6. 通知相關方
7. 使用撤回確認更新UI

**輸出**：
- 撤回確認
- 更新的訊息狀態
- 活動日誌條目

**業務規則**：
- 只能撤回待處理訊息
- 撤回必須在排程傳送時間前發生
- 客服只能撤回自己的訊息
- 團隊主管可以撤回團隊訊息
- 撤回活動記錄以供審計

#### 5.2.3 佇列處理 (FR-MSG-006)
**描述**：處理延遲訊息傳送佇列
**處理器**：`queue-consumer.ts`

**處理流程**：
1. 從Cloudflare Queue接收訊息
2. 驗證訊息仍為待處理
3. 為傳送處理訊息內容
4. 透過平台API發送訊息
5. 基於傳送結果更新訊息狀態
