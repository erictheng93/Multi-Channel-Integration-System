流程說明

  • 客戶端不需登入本系統，身分由 LINE / Facebook 平台提供，以 (platform, platformUserId) 唯一識別。
  • 客服端一律經 JWT 雙令牌驗證；token 內已快取 allowedTeamIds[] 與 teamRoles{}，支援一人多團隊、不同團隊不同角色。
  • 對話指派自 v4 起為團隊指派（個人指派已退場），跨團隊轉移會寫入 conversationTransfers 保留歷史。
  • 四個門戶共用同一套資料層，差別在權限範圍而非獨立系統；Admin 為全域，其餘受團隊範圍限制。
  • 所有 UI 更新的主要路徑是 WebSocket 廣播，D1 輪詢僅作為次要備援。

主要資料流向（範例）

  1. 客戶進站：LINE Webhook → 簽章驗證 → 建立/更新客戶 → 建立或指派對話 → 寫入 D1 → 自動回覆評估
  2. 即時推播：訊息寫入 → MessageBroadcaster → ConversationRoom / UserConnection → 前端 Pinia store
  3. 客服送訊：寫入 D1 → DelayedMessageScheduler（DO Alarm）→ 撤回視窗 → 到期 → LINE Push API
  4. 事件擴散：對話事件 → 通知中心 / 活動記錄 / 稽核日誌 / 分析聚合
  5. 非同步後處理：LINE_MESSAGE_QUEUE → 消費者 → 重試 → 失敗進 line-message-dlq

備註 — 現況與已知落差

  • 部分完成 Facebook Messenger：收訊與 LINE 同級，送訊尚未接通（delivery service 只處理 line 分支），客服目前無法回覆 FB 客戶。
  • 僅 LINE 自動回覆與延遲訊息緩衝目前只對 LINE 客戶生效；FB 訊息直接送出，事後靠 Graph API 刪除。
  • 受限 延遲秒數為單一全域設定的 5 檔（0 / 30 / 60 / 120 / 300 秒），無逐則覆蓋、無改期端點。
  • 未啟用 Email / Push 通道為停用的模擬實作；實際唯一送達通道是應用內 WebSocket。
  • 縮水 報表系統宣告 24 種類型，實際可產出 3 種，且只有 JSON / CSV 真正序列化。
  • 單一事實來源 各項完成度以 docs/PROJECT_OVERVIEW.md 為準，本圖僅為流程總覽。
